# 跨语种检索靠多语 embedding，不做查询翻译

## 背景

五语语料（zh/en/de/nl/es）× 五种用户提问语言 = 25 种组合。朴素做法会掉进两个坑：

1. **副本稀释**：同一段内容有 5 个语言副本，向量空间里挤成一团，top5 全是同义重复，等于只召回一条信息
2. **全文检索在多语上失效**：`to_tsvector('simple', …)` 不做词干化，德语 `Wechselrichter` / `Wechselrichters` 被当成两个词，荷兰语复合词切不开

## 决定

- **向量路**负责语义与跨语言对齐：多语 embedding（`text-embedding-v3`，1024 维），查询时 `WHERE lang = any(ARRAY[用户语言, 'en'])` **强制语言过滤**
- **全文路**只负责术语精确命中：故障码、型号、规格数字
- 两路 **RRF 融合**，向量权重 0.8、全文权重 0.2，`k=60`
- **不做** query 翻译。不把德语问题翻成中文再检索。

## 为什么不做查询翻译

多一次 LLM 调用 ≈ +1.5s 延迟；更糟的是翻译错误会污染整条链路——用户看到的是德语答案，但检索用的是错的德语译中。多语 embedding 已经在共享空间里对齐了语种，不需要多此一举。

## 容易写错的地方

RRF 原始分在 `0.013` 量级，**必须归一化**后才能和 `RETRIEVAL_MIN_SCORE=0.30` 比较。直接比会导致 100% 拒答。这是本项目最高频的踩坑点。

## 代价

- embedding 必须支持多语且维度固定 1024，换模型就得重建 `chunks` 表
- 语言过滤条件一旦漏写，召回会悄悄劣化（指标从 0.75 掉到 0.3），但服务不报错

## 会怎么被推翻

若 hit@5 长期低于 0.60 且确认不是分块问题，再考虑两段式：先向量召回 20 条跨语言，再用小模型做跨语重排。成本是多一次模型调用。
