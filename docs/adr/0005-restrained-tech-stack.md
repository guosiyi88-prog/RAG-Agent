# 刻意不用 ORM、不用前端构建链、不用测试框架

## 背景

一个 8–11 小时要交付的演示系统。技术选型的唯一标准是：**减少故障点**，不是"符合工程规范"。

## 决定

| 不做 | 改用什么 |
|---|---|
| ORM（Prisma / Drizzle） | `pg` 手写 SQL，18 张表 |
| 前端构建（Vite / webpack / TS 编译） | 两个 `.html` + 两个 `.js`，浏览器直接跑 |
| 单元测试框架（Jest / Vitest） | 一个 `scripts/eval.ts` 集成验证 |
| Lint（ESLint / Prettier） | `tsc --noEmit` |
| Tailwind CDN | 手写 400 行 `app.css` |
| 队列（BullMQ） | 进程内会话池 |
| dotenv | Node 22 的 `--env-file` |
| LangChain / LlamaIndex | Pi SDK 本身就是运行时 |

## 为什么这是刻意为之

未来的工程师会本能地想"补上"这些。先说清楚为什么没有：

- **每一层抽象都是一次静默失败的机会**。ORM 生成的 SQL 你看不见，出问题时只能猜。
- **构建链在演示现场是纯负资产**。多一个 `npm run build` 就多一个"忘了构建"的翻车点。
- **18 张表的项目不需要 ORM**。手写 SQL 更快，且能用上 pgvector 的 `<=>` 操作符（ORM 大多要绕）。
- **测试框架覆盖率不到 5% 时，价值低于配置成本**。真正有效的验证是 `make eval` 跑 30 题和 5 个代码闸门。

## 代价

- 手写 SQL 会有重复代码，接受
- 没有类型安全的前端，靠人读代码（这是 G4 闸门存在的理由）
- 重构时没有测试兜底，所以规格必须准（这是整套 PRD 存在的理由）

## 会怎么被推翻

项目从演示转生产、代码量过万行时再引入。现在引入只会拖慢交付。
