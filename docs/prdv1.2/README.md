## 一、这一版为什么存在

v1.1 是**开工前**写的规格，它的任务是"让 AI 只看文档就能写完代码"。实做过程中产生了三类 v1.1 里没有的东西：

1. **被裁定的规格冲突**。最典型的是内部接口失败形状：v1.1 一处写 401、一处写 404，实现选了 404 并把理由写进了 `src/auth.ts` 的注释。这类裁定如果只活在注释里，下一个接手的人会把它当 bug 改回去。
2. **实现级的硬约束**。例如"工具必须经扩展注册、会话创建时只做筛选"、"`reply.hijack()` 之后状态码就写不动了，所以池满必须在开流前变成 503"。这些是踩出来的，v1.1 里没有。
3. **真实的账**。v1.1 的计划是 12 张任务卡；实际落账是 **8 个 spec / 19 张工单**（`.scratch/`），每张开在哪、卡在哪个闸门，v1.1 的 `15-tasks.md` 已经对不上了。

v1.2 让这三类东西有一个**正式的家**，并且把"文档 ⟷ 代码"的漂移变成一条可执行的纪律（§七）。

## 二、取证规则（怎么读这一版）

**证据优先级**（高 → 低）：

```
sql/*.sql 与 src/**            决定性（含注释里已裁定的理由）
tests/**                       行为已被钉住的证据
scripts/**（ingest/eval/verify）流程与门槛的证据
.scratch/**/spec.md|issues/*   决策与卡边界的证据
docs/prdv1.1/**                设计意图，只用于对照
```

四条写法约定：

1. **只写"是"，不写"应该"**。需要表达设计意图时，标注「意图」并给出处。
2. **机械事实不重抄**。列名、键名、常量值一律给 `path:line`，文档只写**语义与不变量**——抄一遍就多一个漂移点。
3. **冲突以代码为准**，并把冲突登记进 `16-risks-errata.md` §2（E 编号），不静默修正。
4. **同一事实只在一个地方定义**：鉴权口径在 `src/auth.ts`、错误码在 `src/errors.ts`、运行参数在 `src/config.ts`、文案键在 `src/static/i18n.json`。文档重复描述时只描述"为什么"，不复述"是什么"。

## 三、与 v1.1 的关系

| 维度 | v1.1 | v1.2 |
|---|---|---|
| 性质 | forward spec（做完之前） | as-built spec（做完之后） |
| 读者 | 要写代码的 AI | 要维护、评审、接手的人 |
| 任务口径 | T00–T11 任务卡 | **8 spec / 19 工单**（真实落账） |
| 已知限制 | L1–L12 | L1–L12（沿用）+ **E 系列**（实现期新增，见 16 §2） |
| 已知冲突 | 未裁定（如内部 401/404） | 已裁定，并写进对应章节 + 16 §2 |
| 状态 | 冻结，不再维护 | 随代码维护，改动必须同步 |

`docs/prdv1.1/` **保留不删**：它是"当时的意图"，评审时用来回答"为什么这么做"；v1.2 回答"现在是什么样"。

## 七、维护纪律（改代码的人必须读）

1. **一改一改**：改 DDL → 改 `04`；改路由/错误码 → 改 `05`；改检索常量 → 改 `07`；改文案键 → 改 `12`；改 env → 改 `13`；改验收命令 → 改 `14`；改任务状态 → 改 `15`。
2. **新增能力要占两个位置**：`01`（范围里加一行）+ `15`（工单账里加一张卡）。只在代码里加，等于没做交接。
3. **发现文档与代码不一致**：先在 `16` §2 登记一个新 E 编号，再改文档。反过来做（直接改文档）会把"什么时候漂的"永久丢掉。
4. **不许在 v1.2 里写实现计划**。计划只出现在 `15` §5，且必须带"完成判据"。
5. **`docs/prdv1.1/` 一个字都不要改**。它的价值就在于冻结。

## 八、本次逆向发现的偏差去哪了

实现与 v1.1 的每一处实质差异，都收敛在 `16-risks-errata.md` §2 的 **E 系列**里，每条给：`现象 → 证据（文件:行）→ 裁定（以谁为准）→ 对使用者的影响`。

同时保留 v1.1 原有的 **L1–L12 已知限制**（16 §3），二者不合并：L 是"功能上故意不做"，E 是"文档与实现不一致且已裁定"。
