## 二、为什么是这个顺序（不是提示词的 R1→R2→R3）

1. **S1/S2 不依赖鉴权**，可以立刻开工，不用等人拍边界。原排期里它们被塞在 R3 末尾，等于让最不需要许可的活等了最需要许可的活。
2. **S2 必须在 S4 之前**。提示词 §3 已定："先做真源与发布态，再做 UI"。反过来的话，管理端改完的码会被下一次 `make ingest` 静默回滚（R21），演示现场翻车。
3. **S3 是管理端能力的总闸门**。跳过它只做角色化，得到的是"界面按角色显隐、身份仍可自称"的版本——提示词 §3 末句判定它"更糟"，因为审计里写谁都不作数。
4. **S5 排最后**：知识库 CRUD 不改变失败半径（改错一篇文档=一次检索劣化），而故障卡改错=对用户直接给错答案。

## 三、允许与禁止并行

- 允许：S1 与 S2 交错（改的是不同表的不同读点）。
- 允许：S2 的 DDL 与 S3 的 `staff` 密码列分两批提交。
- 禁止：S2 与 S3 **同时**改 `src/auth.ts`（一个是查询侧、一个是鉴权，冲突面为零但 review 面会糊）。
- 禁止：S4 在 S2 完成前开工。
